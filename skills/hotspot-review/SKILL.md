# 熱點架構審查

只看最近常被修的地方：重構在那裡才真的省事，很久沒人動的程式寫得再醜也不花時間。
但被修很多次不代表結構有問題（文案修正、上線當天的跟進、上游資料改寫都會累積次數）。
這個 skill 的價值是讀完每個 fix 的 diff 後，誠實說「有共同根因」或「沒有」。
實際跑起來，常常 5 個熱點只有 1 個值得做；報告說「不建議」是正常結果，不要硬湊。

## 開始前

讀 repo 的 `AGENTS.md`（或 `CLAUDE.md`）：刻意分離、ADR、禁區、合併與 CI 規則都以它為準。
再依序讀下面三份追加設定，存在就讀，衝突時後面的為準：

1. repo 的 `.agents/hotspot-review.md`：這個 repo 的團隊規則，會 commit（例如不能合併的兩條路徑、要付費或有配額才能跑的指令、`HOTSPOT_NOISE`）。
2. `~/.config/hotspot-review/local.md`：只屬於這台機器、每個 repo 都適用的規則（記憶體、工具偏好）。
3. repo 的 `.agents/hotspot-review.local.md`：只屬於自己、只用在這個 repo 的規則，不 commit（寫進 `.git/info/exclude`）。

分析員也要讀同樣幾份，派工時把實際存在的路徑一起給他。

## 範圍

**預設只做到報告，然後問使用者要做哪幾個。** 使用者或交接單（例如 `/overnight`）明確授權，才往下開 PR、合併；授權以原話為準。

輸入（都可省略）：期間，預設最近 30 天；指定的模組或檔案，有給就跳過自動挑熱點，只看那一塊。

## 第一階段：分析（唯讀）

報告放 repo 外，避免研究產物進 commit：`OUT=~/.local/state/hotspot-review/<repo 名>/<今天日期>`（在 `/overnight` 底下用它的 `$OUT/arch/`）。subagent 的 Write 被擋時，改用 shell heredoc 寫。

### 1. 算熱點

```bash
bash <本 skill 目錄>/scripts/hotspots.sh <起始日> > "$OUT/hotspots.txt"
```

輸出三張表：全部改動次數、fix 改動次數、常一起改的檔案組（已排除文件、changelog、fixture、lockfile，開頭附可重跑的指令）。第二個參數是每張表的列數（預設 30），不是天數。repo 有其他產生檔或雜訊，用環境變數 `HOTSPOT_NOISE` 追加排除的正規式。

### 2. 挑熱點

挑 3 到 6 個熱點，每個是一組常一起改的檔案：

- **優先挑 fix 多的**；只有 feat 多，通常只是新功能還在長。
- 常一起改的併成一組（元件、lib、樣式、smoke）；測試和 smoke 跟著它測的程式走，不單獨成組。
- 總契約檔、型別總表這類天生每次都動的檔案，要看的是跟它一起改的是誰。

每個熱點寫一行到 `decisions.tsv`：檔案、改動次數、fix 次數、初步懷疑（例如「疑似複製版」）。沒挑的明顯候選也寫理由。懷疑只給分析員方向，不是結論。

### 3. 派分析員

每個熱點派一位 subagent，全部同時在背景跑、只讀。要能寫輸出檔，所以用能寫檔的一般用途 agent（Claude Code 不用 Explore），用你能用的最強模型。宿主不能開 subagent 時，就自己依序照 analyst-brief 逐個熱點做，每做完一個寫完檔再做下一個。每位約 15 萬 token、5–8 分鐘，開跑前心裡要有數。給每位：

- `references/analyst-brief.md` 的路徑（照它做）
- 熱點檔案清單、期間、你的初步懷疑
- 輸出檔：`$OUT/hotspot-<N>.md`

分析員只回 10 行內摘要，完整內容在檔案裡，避免 diff 塞滿主線 context。

### 4. 寫報告

讀完所有分析員的檔案，寫 `$OUT/report.md`。依序用這 4 條排序，任何一條不符就列在「不做」並寫原因：

1. **根因是同一個設計問題**，有至少 2 個痛點 SHA 佐證。痛點 SHA 是「因為這個設計問題才需要的 fix」：revert 後原樣重送只算一個；第一次把重複寫進來的 commit 是成因不是痛點；上線當天的跟進、純文案或配色不算。
2. **能純結構地做**：不碰錢、時間、權限、資料的計算規則，不違反 AGENTS.md 的刻意分離和 ADR。
3. **有保護測試或補得出來**，而且不需要付費、有配額或連正式環境的指令就能驗證。
4. **閱讀負擔真的會下降**：刪掉一份規則、合併重複判斷、移除死碼。只是搬家或多包一層不算。

收攏時常會發現現況前後不一致，一收攏就改到行為。這時不要整個放棄，拆成兩半：**結構那半**用特徵測試固定現況，照樣當純重構排序；**統一行為那半**放進「需使用者決定」。細節見 `references/refactor-phase.md` 第 3 節。

報告結構：

```
# <repo> 熱點架構審查（<期間>，origin/main <sha>）

## 總結
建議做幾個、各一句話；不做幾個；需要使用者決定的事。

## 熱點與結論
每個熱點一節：檔案、根因摘要、痛點 SHA、建議或不做的理由。
建議的寫新形狀、呼叫端、保護測試、預估 diff。
不做的寫原因（沒有共同根因／已經收斂／違反刻意分離／碰到口徑／證據不足）。

## 需使用者決定
不屬於純重構的事（前後不一致的行為、口徑差異），每件 2 個選項、標建議、寫影響。

## 小發現
過時註解、幾行重複程式，下次改到附近時順手處理。

## 方法
hotspots.txt、hotspot-N.md 的位置，判斷標準。
```

### 5. 交給使用者

白話回覆：建議做哪幾個、各自為什麼、幾件事要他決定，附 `report.md` 路徑。

接著用選擇題問（宿主有選擇題工具就用，沒有就在對話裡列編號選項）「要做哪幾個？」，選項包括「全部建議的」「只做第 N 個」「先不做」。「需使用者決定」的事也一起問，這些每題 2 個選項、建議的放第一。使用者不在（例如 `/overnight`）就不問，照交接單授權做，沒授權的留在報告裡。

## 第二階段：重構（需授權）

讀 `references/refactor-phase.md`，一個一個照步驟做：開 worktree、固定行為、只改結構、新舊對照、開 PR、獨立 reviewer、squash 合併、確認 main CI。

最多 3 個：再多 review 和 CI 會塞車，第 4 個通常證據也不足了。

## 紀錄

每個非顯而易見的決定（挑或不挑熱點、不做某個重構、review 結果、合併）寫一行到 `$OUT/decisions.tsv`：時間、決定、理由、還原方式（`git revert <sha>`、`gh pr close <N>`）。

## 不做的事

- 不部署。
- 不 force-push、不 rebase、不 `--no-verify`、不 `--admin`；衝突用 `git merge origin/main` 解。
- 不為了變綠改測試期望值，也不停用 check。
- 不跑要付費、有配額或連正式環境的指令；驗證需要它就跳過那個重構，寫進報告。
- 不碰別人的 branch 和 open PR 改到的檔案；開工前用 `gh pr list` 查重疊。
